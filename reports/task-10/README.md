## 一、界面方案

### 1. 视觉
- 暗色主题，颜色全部集中在 `:root` 的 CSS 变量里（背景 `#0f1216`、面板 `#171b21`、强调色 Dota 金 `#e0a63a`、胜 `#4cc38a`、负 `#e5595b`），移植时整段 `<style>` 可直接替换现有样式。
- 胜负用**行首色条 + 文字**双重编码，不只靠颜色区分。
- 字体栈优先 PingFang SC / 微软雅黑 / Noto Sans SC，不引入 Web 字体（省一次请求）。

### 2. 信息架构调整
| 位置 | 现状（据任务帖） | 调整 |
|---|---|---|
| 顶栏 | 查询框 | 吸顶；查询 + 「刷新」（对应 `POST /players/{id}/refresh`，点后给出「约 1–2 分钟后可见」的提示） |
| 玩家卡 | — | 常驻于标签之上：昵称、ID、段位中文名、总场次、胜/负、总胜率、近 20 场战绩。四个标签共享，不用来回切 |
| 标签栏 | 四个标签 | 保留四个，吸顶在顶栏下方；当前标签写进地址栏 `#/<id>/<tab>`，可收藏、分享，刷新不丢 |
| 最近比赛 | 一次渲染 100 场 | 全部/胜利/失败筛选；每次渲染 20 场，「加载更多」追加 |
| 英雄统计 | — | 中/英文名搜索；按场次/胜率/KDA 排序；胜率条（<50% 红色） |
| 队友 | — | 按同队场次排序，显示同队胜率条、对抗场次；每行「对比」按钮一键跳到对比页 |
| 对比 | 需要输两个 ID、5 个请求 | 左边固定为当前玩家（复用已加载数据），只输对方 ID；逐项高亮较优值；各自常用英雄 Top3 |

### 3. 响应式（375px）
断点 640px。手机端：
- 比赛行由 6 列表格变成两行卡片：左侧英雄 + 「时间 · 时长 · 模式」，右侧结果 + KDA；
- 英雄统计 / 队友行把胜率条放到第二行占满宽度；隐藏次要列（场均 K/D/A、对抗场次）；
- 表头在手机上隐藏；标签按钮等宽平分。
- 已在 375×812 视口实测：页面 `scrollWidth = 375`，无横向滚动；查询、切换标签、筛选、加载更多、队友→对比均可用。

### 4. 交互细节
- 加载中显示骨架屏；查询非数字 ID 直接提示，不发请求。
- 连续查询两个 ID 时，只渲染最后一次的结果（`state.id` 比对，丢弃过期响应），避免旧数据覆盖新数据。
- 所有面板用事件委托，重绘时不重复绑定监听器。

## 二、中文化约定

- 界面文案全部中文；英雄统一显示中文名，副标题显示英文名（便于和英文攻略对照），搜索同时匹配中英文。
- 英雄名以 `heroes-zh.json` 为准（国服客户端通用译名）。查不到的新英雄回退显示 API 的 `localized_name`（mock 里显示「未知英雄」）。
- 段位 `rank_tier`：十位为段位，个位为星数。1 先锋、2 卫士、3 中军、4 统帅、5 传奇、6 万古流芳、7 超凡入圣、8 冠绝一世（冠绝不显示星数）。例：`75` → 超凡入圣 5。
- 游戏模式 `game_mode`：1 全阶英雄、2 队长模式、3 随机征召、4 单一征召、5 全部随机、16 队长征召、18 技能征召、22 全英雄选择、23 加速模式；其余显示「其他模式」。
- 胜负判定：`player_slot < 128` 为天辉，`(player_slot < 128) === radiant_win` 即胜。
- 时间：一小时内「N 分钟前」，一天内「N 小时前」，30 天内「N 天前」，更早显示日期。

## 三、性能优化方案

### 1. 现状诊断（基于任务帖 2026-09-27 NAS 实测）

| 请求 | 耗时 | 体积 | 现有缓存 |
|---|---|---|---|
| heroes | 0.68s | 22KB | 24h |
| players/{id} | 0.82s | — | 60s（落入「其他」） |
| players/{id}/wl | 1.08s | — | 60s |
| players/{id}/matches?limit=100 | 0.76s | 26KB | 60s（见下方注） |
| players/{id}/peers | 0.82s | 20KB | 60s |
| Steam CDN 单张英雄图 | ≈1.07s | — | 浏览器缓存 |

判断：
1. **数据请求不是主要瓶颈。** 5 个请求在浏览器里并行，冷启动墙钟约等于最慢的一个（wl 1.08s）。但玩家数据只缓存 60s，隔一分钟再看又是全量冷请求。
2. **图片是「卡」的主因。** 英雄统计一次渲染几十行，每行一张 ≈1.07s 的外网图；现有页面如果用的是整幅英雄立绘，体积和解码开销还会更大。浏览器对同一域名的并发有限，几十张图会排队，列表迟迟填不满，滚动时还会因为图片没占位而抖动。
3. **对比页浪费。** 5 个请求里当前玩家那一半数据早已加载过；且对比用 `matches?limit=50`，和主查询的 `limit=100` 缓存 key 不同，无法复用。

> 注：任务帖写的是「`matches/` 前缀 1h」。如果实现是 `path.startsWith('matches/')`，那它只命中比赛详情 `matches/{match_id}`，`players/{id}/matches` 实际走的是 60s。请 kimi-nas 核对 server.js 的匹配方式。

### 2. 目标

| 指标 | 现在 | 目标 |
|---|---|---|
| 首屏浏览器请求数（数据） | 5 | **1**（`GET /api/player/{id}/summary`） |
| 首屏上游 OpenDota 请求数 | 5（冷） | 冷 **4**（heroes 静态化后为 0），热 **0** |
| 首屏数据墙钟 | ≈1.1s，60s 后重来 | 冷 ≈1.1s；10 分钟内再看 < 0.1s（NAS 本地） |
| 首屏图片数 | 几十张 | ≤ 20 张 32px 小图标，并懒加载 |
| 图片单张延迟 | ≈1.07s（外网） | 二次访问起 ≈ 局域网延迟（NAS 本地磁盘缓存） |
| 对比页上游请求 | 5 | 冷 3，热 0；当前玩家 0 |

### 3. 具体措施（按收益/成本排序）

**P0 图片策略（收益最大，改动约 30 行）**
1. 列表用小图标 `.../dota_react/heroes/icons/{key}.png`（32×32），不用立绘。mock 已用，已实测该路径可用。
2. `<img loading="lazy" decoding="async" width="32" height="32">`：只加载视口内的图，固定尺寸防止布局抖动。mock 已实现。
3. 分页渲染：比赛列表每次 20 行，首屏最多 20 张图。mock 已实现。
4. 失败占位：捕获阶段一个 `error` 监听器，把加载失败的图换成中文首字块，CDN 不通时页面也不难看。mock 已实现。
5. NAS 端图片代理：新增 `GET /img/hero/{key}.png`，第一次从 Steam CDN 取回后写入本地磁盘，响应头 `Cache-Control: public, max-age=31536000, immutable`。之后所有设备都从 NAS 取，1.07s 变成局域网毫秒级。约 30 行，零依赖（`https` + `fs`），`key` 需用 `/^[a-z_]+$/` 白名单校验，防路径穿越。

**P1 请求合并 + 缓存 TTL（改动约 60 行，前端数据层要改）**
1. 新增 `GET /api/player/{id}/summary`：服务端并行拉 profile / wl / matches?limit=100 / peers，合成一个 JSON 返回。浏览器从 5 个请求变 1 个，上游并发由 NAS 统一控制，也方便统一处理 429。原 `/api/od/*` 代理保留，不影响现有语义。
2. heroes 静态化：`heroes-zh.json` 作为前端静态文件随版本发布（文件名带版本号或加 `?v=`，长缓存）。首屏少一个上游请求，同时解决中文名问题。新英雄上线时更新该文件即可；前端遇到未知 hero_id 可退回请求一次 `/api/od/heroes`。
3. TTL 调整建议：

| 路径 | 现在 | 建议 | 理由 |
|---|---|---|---|
| heroes / constants | 24h | 7d（静态化后基本不再走代理） | 只随版本更新变化 |
| players/{id} | 60s | 1h | 昵称、头像、段位变化慢 |
| players/{id}/wl | 60s | 10min | 一局比赛至少 20 分钟，10 分钟足够新 |
| players/{id}/matches | 60s（或 1h，待核对） | 10min | 同上 |
| players/{id}/peers | 60s | 1h | 统计量，变化慢 |
| matches/{match_id} | 1h | 30d | 比赛结束后数据不可变 |

4. `POST /players/{id}/refresh` 成功后，删除该 id 下所有 `players/{id}/*` 缓存，保证「刷新」按钮真能看到新数据。
5. stale-while-revalidate：缓存过期后先返回旧数据，同时在后台刷新；上游 429 或超时时继续返回旧数据，并加响应头 `X-Cache: stale`。前端可以提示「数据可能不是最新」。
6. 给内存缓存加条目上限（例如 500 条，按插入顺序淘汰最旧的，`Map` 即可实现），防止 NAS 常驻进程内存持续增长。

**P2 传输（改动约 15 行）**
- JSON 响应按 `Accept-Encoding` 用 Node 自带 `zlib` 做 gzip。matches 26KB + peers 20KB 这类重复字段多的 JSON，一般能压到原来的 20%～30%。
- 静态资源加 `Cache-Control`：`index.html` 用 `no-cache`，带版本号的 js/css/json 用长缓存。

**P3 对比页**
- 当前玩家复用已加载的 summary，只为对方请求一次 summary（与主查询同一 key，缓存可以互相命中）。
- 对比统一用最近 100 场里的前 50 场计算，不再单独请求 `limit=50`。

### 4. 验证方法（给移植后用）
- 在 NAS 上分别冷、热各测一次 summary：`curl -s -o /dev/null -w '%{time_total}\n' http://<nas>/api/player/139369436/summary`，热请求应 < 0.1s。
- 图标体积与耗时对比：`curl -s -o /dev/null -w '%{size_download} %{time_total}\n' https://cdn.cloudflare.steamstatic.com/apps/dota2/images/dota_react/heroes/icons/rubick.png`，再对比立绘路径 `.../heroes/rubick.png`。本次在 mock 中只验证了图标路径返回 32×32 图片，没有测体积。
- 浏览器开发者工具 Network 面板：首屏数据请求应只有 1 个，图片请求数 ≤ 20。
